# ADR-004: Content Controls (w:sdt) as Round-Trip Merge Anchors

## Status: Accepted

## Context

The 3-way merge engine needs a way to match paragraphs in a returned DOCX against their originals in the database. Without a stable identifier, matching must rely on position (breaks if paragraphs are inserted or deleted), text similarity (breaks if text is modified — which is the point), or structure heuristics (unreliable).

The OOXML spec provides content controls (`w:sdt` elements) that can carry arbitrary custom XML tags. These survive save/close/reopen cycles in Word. They are preserved by LibreOffice. Their stability through normal editing workflows is the critical question.

Alternative: embed UUIDs as hidden text (vanish character style) or in paragraph properties. Hidden text is strippable. Paragraph properties don't survive Format Painter or paste operations reliably. Content controls are the strongest available anchor in the OOXML spec.

## Decision

Every paragraph generated by SpecR is wrapped in a `w:sdt` content control with a custom XML tag containing the paragraph's UUID:

```xml
<w:sdt>
  <w:sdtPr>
    <w:tag w:val="specr-uuid-7f3a1b2c-..."/>
    <w:alias w:val="SpecR paragraph"/>
    <w:lock w:val="sdtContentLocked"/>
  </w:sdtPr>
  <w:sdtContent>
    <w:p>...</w:p>
  </w:sdtContent>
</w:sdt>
```

The merge algorithm:
1. On re-parse, extract UUID tags from `w:sdt` elements
2. Paragraphs with matching UUIDs → compare text for modification
3. UUIDs in database but not in returned DOCX → deleted
4. Paragraphs in returned DOCX with no UUID → added (new content from the editor)

## Consequences

- **Known risk:** Content control survival rate across different Word versions, LibreOffice, and Google Docs is unknown. This is the single highest-risk assumption in the MVP. We must test this with real editing workflows across Word 2016, Word 365, LibreOffice 24.x, and Google Docs before claiming the merge engine is reliable. See `docs/research-executive-summary.md` § "Open Questions."
- **Phase 3 acceptance status:** CI now tests the round-trip engine with a SpecR-generated DOCX whose `word/document.xml` is edited through JSZip by changing one `w:t` text node while preserving the surrounding `w:sdt/w:tag` anchor. This proves parse → generate → diff → merge when anchors survive. Application survival remains a manual matrix: Word 2016 (not yet certified), Word 365 (not yet certified), LibreOffice 24.x (not yet certified), Google Docs (not yet certified).
- `w:lock: sdtContentLocked` prevents editors from accidentally breaking the structure, but the entire control can be deleted (which we interpret as paragraph deletion — correct behavior).
- Paragraphs pasted from outside SpecR-generated documents will not have UUID tags. The merge engine treats these as additions — correct behavior.
- If content controls are stripped by an application (e.g., a PDF converter that round-trips back to DOCX), the merge falls back to position-based heuristics with lower confidence. This is a degraded mode, not a failure mode.
