## 1. Goal

Let a user manually associate an existing `style_templates` row with a spec — the narrowest
useful slice of #125's three style sources. `.SEC`/`.txt`/PDF masters carry no adopted visual
style; this gives the generator (#32 / WT-6, out of scope here) a real house style to render with.
One template per spec, for now.

## 2. Storage (migration `027_spec_style_source.ts`, reversible)

Nullable FK column on `specs`, **`ON DELETE RESTRICT`**:

```sql
-- up
ALTER TABLE specs
  ADD COLUMN style_template_id uuid REFERENCES style_templates(id) ON DELETE RESTRICT;
-- down
ALTER TABLE specs DROP COLUMN style_template_id;
```

- **Nullable** — `NULL` = "no style source yet," an honest, flaggable state (a spec may legitimately
  lack one; surfacing those gaps as errors is the conformance-audit job #145, not this issue). We
  **never** auto-null an association.
- **`RESTRICT`, deliberately not `SET NULL`** (owner decision): a spec must never silently lose its
  formatting because a template was deleted. A template that any spec references **cannot** be
  deleted — see §5.

## 3. HTTP surface

```text
POST   /specs/:id/style-source   body { templateId: uuid }   → assign (replaces existing)
DELETE /specs/:id/style-source                                → clear (back to generator defaults)
```

- `POST`: validate body via `validateBody(Zod { templateId: z.uuid() })`.
  **Pre-check existence explicitly** (do not rely on the FK error — see §6): unknown spec → **404**
  "spec not found"; unknown template → **404** "template not found". Re-assign overwrites.
  Success → 200 with the updated style source (`{ templateId, templateName }`).
- `DELETE`: unknown spec → 404; otherwise clear and return 200 (idempotent — clearing an already-null
  association is still 200).
- Handlers live in a new `src/api/style-source.ts`; routes registered in `router.ts` next to the
  other `/specs/:id/*` routes.

## 4. Read surface — disjoint from #134

Issue `#134` modifies `getSpecTree` / `buildNodeTree` in `src/db/queries/specs.ts`. To keep the two issues'
DB code **non-overlapping**, #138 surfaces its association via a **separate query merged in the API
handler**, never by touching `getSpecTree`:

- New `src/db/queries/style-source.ts`, re-exported from `src/db/index.ts`:
  ```ts
  getSpecStyleSource(specId): Promise<{ templateId: string; templateName: string } | null>
    // SELECT s.style_template_id, t.name FROM specs s
    //   LEFT JOIN style_templates t ON t.id = s.style_template_id WHERE s.id = $1
    // returns null when spec has no template (or spec absent — caller already 404s)
  setSpecStyleSource(specId, templateId): Promise<boolean>  // false when spec is missing → 404
  clearSpecStyleSource(specId): Promise<boolean>            // false when spec is missing → 404
  countSpecsUsingTemplate(templateId): Promise<number>   // for the RESTRICT 409 message (§5)
  ```
- `getSpecHandler` (`src/api/specs.ts`) extends its response: `data: { ...tree, styleSource }`,
  where `styleSource = await getSpecStyleSource(id)` (`{ templateId, templateName } | null`). This
  adds a sibling field to the existing flat tree response — existing consumers unaffected.
- MCP `get_spec` (`src/mcp/handlers.ts` + `tools.ts`) surfaces the same `styleSource` field, per the
  stateless-server / `z.uuid()` / `isError` conventions (import DB fns from `../db/index.js` only).

## 5. Deletion protection (the RESTRICT enforcement — #138 owns this)

A template referenced by any spec must not be deletable. Implement as an **explicit pre-check**, not
a caught FK error (clearer message, avoids the 23503 ambiguity in §6):

- `deleteTemplate` (`src/db/queries/templates.ts`) — before the `DELETE`, call
  `countSpecsUsingTemplate(id)`; if `> 0`, signal "in use" to the caller. Keep the function's
  contract clean (e.g. return a discriminated result `{ deleted: true } | { deleted: false, reason:
  'not_found' | 'in_use' }`, or throw a typed in-use error — implementer's choice; the 409 outcome
  is the contract, not the mechanism).
- `deleteTemplateHandler` (`src/api/templates-crud.ts`) — map the in-use outcome to **409 Conflict**
  with `"template in use by N spec(s)"`; `not_found` → 404; `deleted` → 200/204 as today.
- Existing template-CRUD tests must stay green; add a test that delete-while-referenced → 409 and the
  template still exists afterward.

## 6. The 23503 ambiguity (why pre-checks, not the generic mapper)

`pgErrorToHttp` (`src/lib/pg-errors.ts`) maps pg `23503` (foreign_key_violation) → **404** by default.
But `23503` fires in two opposite situations here:
- assign a spec to a **missing template** → 404 is correct;
- delete a template **still referenced** → must be **409**, not 404.

One code, two meanings — the generic mapper can't disambiguate. Therefore both paths pre-check
explicitly (template existence on assign; reference count on delete) and return the right status
directly, never falling through to the ambiguous FK mapping.

## 10. Out of scope (per issue + owner discussion)

- **Project-level style + inheritance** (the "spec inherits its project's style; move spec A→C and
  project C's style applies" model). That is #125 / ADR-015 *inherit*. #138 builds only the spec-level
  manual-pick layer — the **top** of the future resolution chain:
  `effective = spec.style_template_id ?? project.style_template_id ?? generator default`. The nullable
  column here is forward-compatible with that chain; building the project layer is a separate issue.
- Generator *consumption* of the association (#32 / WT-6). Per-paragraph style overrides (WT-4).
  Conformance flagging of style-less specs (#145).
