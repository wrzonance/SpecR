# Design: Text Parser Anomaly Surfacing — `meta.warnings` on `CsiTree`

**Issue:** [#68](https://github.com/wrzonance/SpecR/issues/68) — `feat(parser): parse anomaly surfacing — meta.warnings on CsiTree, parse-warnings capability`

**Date:** 2026-05-18
**Phase:** 1c
**Status:** Approved

## Problem

When the text parser detects structural anomalies during parsing, it currently fails silently. The output tree is wrong with no indication of why.

The most common silent failure: `pushContinuation` (`src/parser/text/index.ts:60`) drops continuation lines that appear before any structural node. If a UFGS plaintext file has specifier-note bracket bleed before the first `PART`, those lines vanish from the parsed output and the user has no way to detect it.

## Goal

Surface three structural anomalies as typed warnings on the parsed `CsiTree`. Make them observable through the existing REST and MCP surfaces without inventing new endpoints or middleware.

This is the observability layer for the text parser — analogous to `meta.conflicts` in the DOCX parser (#56).

## Architecture

Text parser gains a post-build anomaly detection pass. Warnings attached to `CsiTree` only when present (sparse — `undefined` when no anomalies). `parseText` adds `'parse-warnings'` to the existing `capabilities` array when warnings are emitted. No new modules.

Detection runs entirely client-side of the DB. Warnings never persisted (Phase 1c) — they ride in the parse-job result envelope and disappear once consumed.

## Types — `src/ast/types.ts`

```typescript
export type ParseWarningType =
  | 'root-continuation'
  | 'empty-part'
  | 'no-structure-found';

export interface ParseWarning {
  readonly type: ParseWarningType;
  readonly lineHint?: string;   // format: "line N: <snippet>" — combined line + text
  readonly suggestion?: string; // hardcoded per warning type
}

export interface CsiTree {
  readonly id: string;
  readonly section: string;
  readonly title: string;
  readonly parts: readonly CsiNode[];
  readonly warnings?: readonly ParseWarning[]; // sparse — only set when anomalies found
}
```

## Detection — `src/parser/text/index.ts`

`buildTree` refactored to return both the parts array AND a structured trace of dropped root continuations and the line index at which each `part` node was created. Line index is tracked by enumerating `lines` (already produced by `text.split(/\r?\n/)`) with the existing loop, so the change is local.

New internal return shape:

```typescript
interface BuildResult {
  readonly parts: readonly CsiNode[];
  readonly droppedAtRoot: readonly { line: number; text: string }[];
  readonly partLineIndex: ReadonlyMap<string, number>; // partNodeId → 0-indexed line number
}
```

After `buildTree`, `parseText` runs `detectWarnings(buildResult)`. Returns `readonly ParseWarning[]`. If non-empty, `parseText` attaches it to the returned tree and adds `'parse-warnings'` to `capabilities`.

### Detection rules

| Warning type | Detection rule | `lineHint` format | `suggestion` (hardcoded) |
|---|---|---|---|
| `no-structure-found` | `parts.length === 0` | `undefined` (whole-doc condition) | `"No PART/Article/list-prefix lines detected. Check for non-standard numbering or PDF/encoding corruption."` |
| `empty-part` | any `part` with `children.length === 0` | `"line N: <part.text>"` — N from `partLineIndex` | `"Part has no Articles. May indicate truncated content or unrecognized child prefixes."` |
| `root-continuation` | `droppedAtRoot.length > 0` — one warning per drop, capped at first 5 | `"line N: <text>"` (per drop) | `"Continuation text appeared before first structural heading and was dropped. Possible noise-prefix bleed; consider whether this line should be a heading."` |

`WARNING_SUGGESTIONS` is a single `const` map in the same file. No i18n, no per-instance text customization.

**Cap at 5** for `root-continuation` prevents pathological docs (PDF extracts with hundreds of pre-PART lines) from producing huge warning arrays. Cap is a constant, not configurable.

## Surface

- **REST:** warnings travel on the `CsiTree` already returned in the parse job result envelope. No new routes, no middleware change. `capabilities` array adds `'parse-warnings'` when `tree.warnings?.length > 0`.
- **MCP:** `parse_document` tool returns the same job result — no changes needed in `src/mcp/tools.ts`.

## Tests

### Unit — `src/parser/text/warnings.test.ts` (new file)

All driven by inline string fixtures. Each test names the symptom.

- `'no-structure-found: empty doc → tree.warnings has no-structure-found, capabilities includes parse-warnings'`
- `'no-structure-found: prose-only doc with no PART/article prefixes → no-structure-found warning'`
- `'empty-part: PART 1 followed immediately by PART 2 with content → empty-part warning on PART 1 with lineHint'`
- `'root-continuation: prose lines before first PART → root-continuation warning, dropped text appears in lineHint'`
- `'root-continuation cap: 10 dropped lines → exactly 5 warnings emitted, all type=root-continuation'`
- `'no anomalies: well-formed UFGS structure → tree.warnings undefined, capabilities does NOT include parse-warnings'`
- `'capabilities array unchanged on no-anomaly path (still ["read-only"])'`

### Integration — `src/api/parse-warnings.integration.test.ts` (new file)

One end-to-end test using a real fixture.

- Fixture: `tests/fixtures/text/anomaly-empty-part.txt` — synthetic UFGS-like file with `SECTION 09 91 00`, `PART 1 GENERAL` populated, `PART 2 PRODUCTS` declared but with no child articles, `PART 3 EXECUTION` populated.
- POST `/parse` → poll job until complete → assert:
  - `result.tree.warnings` is a non-empty array
  - At least one warning has `type: 'empty-part'`
  - `result.capabilities` includes `'parse-warnings'`
  - Other parsing still works (PART 1 and PART 3 trees populated correctly)

## Out of scope

- DOCX parser warnings (#56 — separate issue, different signal source).
- Persisting warnings to the database (`paragraphs` / `specs` tables get no new columns).
- Auto-recovery: re-classifying dropped continuations as headings is #67's responsibility.
- i18n / localized suggestion text.
- Warning-driven retry or re-parse logic.
- Surfacing warnings on UI (Phase 5).
- A `clear_warnings` MCP tool or any other write path against warnings.
