# Design: Integration Test Race — Serialize via `fileParallelism: false`

**Issue:** [#73](https://github.com/wrzonance/SpecR/issues/73) — `test(infra): integration tests race on shared DB when run in parallel`

**Date:** 2026-05-18
**Phase:** 1c
**Status:** Approved

## Problem

`pnpm test:integration` runs `*.integration.test.ts` files in parallel (Vitest default). Multiple files write to the same PostgreSQL instance concurrently, producing non-deterministic failures:

- `paragraphs_parent_id_fkey` FK violations — parent node not yet committed when a child insert fires from a concurrent transaction
- `specs_section_source_unique` duplicate key errors — two test files insert the same fixture spec simultaneously

Tests pass in isolation (`pnpm test:integration <file>`) and in CI (fresh postgres container per run, and the CI runner happens to execute files sequentially). Local developers see flaky failures and waste time investigating phantom regressions.

Observed in `src/parser/sec/index.integration.test.ts` (FK violation) and `src/api/parse.integration.test.ts` (duplicate key on dirty local DB).

## Goal

Serialize integration test file execution so local runs are deterministic. Keep unit tests fully parallel.

## Approach

Add `fileParallelism: false` to the `integration` project block in `vitest.config.ts`. Unit project untouched.

> **Note on Vitest version:** an earlier draft of this spec used `pool: 'forks'` + `poolOptions: { forks: { singleFork: true } }`. That syntax was removed in Vitest 4 (the repo's current version) — `poolOptions` is silently ignored, so the diff did not actually serialize tests when applied verbatim. `fileParallelism: false` is the canonical Vitest 4 replacement and was verified empirically against the original race.

### Why `fileParallelism: false`

- Vitest 4's canonical knob for serializing file execution. Sets `maxWorkers = 1` internally (see `node_modules/vitest/dist/chunks/coverage.DM_a_rWm.js:223`).
- Scoped to the `integration` project, leaving unit-project parallelism untouched.
- Explicit intent: future readers see "serialized on purpose" rather than a generic `maxWorkers: 1` at the top level.

### Rejected alternatives

| Option | Why rejected |
|---|---|
| `pool: 'forks'` + `poolOptions: { forks: { singleFork: true } }` (Vitest 3 idiom) | Removed in Vitest 4 — `poolOptions` silently ignored, so the race was not actually fixed. Original draft of this spec used this; reverted after empirical verification. |
| `vmThreads` + `singleThread: true` | Uses Node `vm` contexts — known incompatibilities with some npm packages (notably native modules and certain pg driver paths). Not worth the risk for a marginal startup gain. |
| `threads` + `singleThread: true` | Worker threads share memory; DB pool singletons could leak state between test files. Adds correctness risk to fix a correctness problem. |
| Top-level `maxWorkers: 1` | Works, but applies globally rather than to the integration project only, and expresses the intent less clearly than `fileParallelism: false`. |
| Per-test DB cleanup helpers | Out of scope. Separate refactor that touches every integration test file. The race is the immediate problem; fix it first, then revisit isolation patterns if needed. |

## Change

Single diff against `vitest.config.ts` (lines 32–38):

```diff
       {
         test: {
           name: 'integration',
           environment: 'node',
           include: ['src/**/*.integration.test.ts'],
           testTimeout: 30_000,
+          fileParallelism: false,
         },
       },
```

No other files modified. No new dependencies. No migrations.

## Verification Plan

1. **Local serial run** — `pnpm test:integration` completes with all integration files passing (14 files / 95 tests at time of merge).
2. **Determinism check** — run `pnpm test:integration` three times back-to-back. All three pass with no FK / unique-key flakes. (Captures the original non-deterministic failure mode.)
3. **Unit test isolation** — `pnpm test` runs in parallel; wall-clock time unchanged vs. main.
4. **Lint + build** — `pnpm lint` and `pnpm build` green.
5. **CI** — PR CI green (already passes by accident before the fix; must not regress).

## Out of Scope

- DB cleanup helpers / per-test isolation refactors.
- Test data factory rework.
- Unit-project configuration.
- CI workflow changes — CI already passes; this is a local-developer correctness fix.
- Regression test for runner config (fragile, low value — verification is empirical).
