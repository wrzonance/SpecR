# Design: numbering-profile `tier` is derived, never authoritative (#319)

- **Date:** 2026-07-11
- **Status:** Approved (brainstorm with thewrz)
- **Issue:** #319 — feat(numbering-profile): make profile `tier` field authoritative in classification
- **ADR:** ADR-067 (to be written in this PR; number centrally assigned — do not renumber)
- **Prior art:** #299 (structural numbering profile), #317 (kept ilvl+articleIlvl authoritative; filed this fork), ADR-061 (read/write schema split), #323 (read-schema hardening)

## Decision

`ilvl` + `articleIlvl` remain the **single classification authority**, exactly as #317 shipped.
The `tier` field on `styleLadder[]` entries and `numbering[].levels[]` becomes an explicitly
**derived annotation**: optional on write, always present and consistent on read, and a write
that declares a `tier` disagreeing with `tierForIlvl(ilvl, articleIlvl)` is **rejected with 422**
— closing the silent no-op that #317's KNOWN AMBIGUITY test documents.

Threading `tier` through classification (the issue's Option 1) is **rejected**, for reasons
ADR-067 must record:

1. No real-world need: no fixture or firm template exists where different numbering ladders sit
   at different offsets in one document (the only scenario a per-entry authoritative `tier` could
   express that the profile-global `articleIlvl` cannot). Confirmed with the maintainer 2026-07-11.
2. Granularity mismatch: `TierName` (`part | article | paragraph | subparagraph`) is coarser than
   the node types classification must produce (`pr1`–`pr7`) — `subparagraph` alone cannot select a
   depth, so `tier` could never fully drive classification anyway.
3. Two competing authorities (`tier` vs `ilvl`) would need precedence rules in the classification
   core for zero demonstrated benefit.

ADR-067 also supersedes the #299 design doc's phrasing that a profile is "authoritative for the
numId→tier mapping": that authority flows through `ilvl` + `articleIlvl`, and `tier` describes
the result. Revisit only if a genuine multi-offset template ever appears (note this in the ADR's
Consequences).

## Mechanism

One cross-field validation on the **write** schema in `src/ast/numbering-profile-schema.ts`
(the ADR-061 read/write split exists precisely so writes can tighten without breaking stored
rows), shared by every write path — REST (`src/api/numbering-profiles.ts`) and MCP CRUD
(`src/mcp/numbering-profile-crud-handlers.ts`) — with **no per-route logic**:

1. **`articleIlvl` becomes required when `styleLadder` or `numbering` is non-empty.** Without it
   the tier check is undecidable at write time (the effective offset would depend on the base
   document at apply time). Extracted profiles always carry `articleIlvl`, so this only affects
   hand-authored partial profiles — a deliberate, approved contract tightening.
2. **Each declared `tier` must equal `tierForIlvl(ilvl, articleIlvl)`** for its entry
   (styleLadder entries and every `numbering[].levels[]` level). `tierForIlvl` lives in
   `src/parser/docx/numbering-profile.ts`; the derivation rule must be shared, not duplicated —
   either export it or move it next to the schema, respecting module boundaries (ast must not
   import from parser; if needed, relocate the pure function into `src/ast/` and re-export from
   the parser barrel so existing imports keep working).
3. **Omitted `tier` is filled server-side** with the derived value, so clients never need to
   compute it; GET → PUT round-trips remain valid.
4. **Error messages name the offending entry and the expected tier**, e.g.
   `styleLadder[2] (styleId "H"): declared tier 'article' but ilvl 3 with articleIlvl 1 derives
   'subparagraph' — to change classification, change ilvl or articleIlvl`. Zod issue → existing
   422 middleware (`src/api/middleware/validate.ts`); MCP returns `{ isError: true, ... }`.

## Read path — unchanged

Stored rows keep reading under the lax read schema (#323 hardening). `applyNumberingProfile`
continues to ignore `tier`. Any pre-existing divergent row remains readable and behaves exactly
as today; it simply can no longer be re-saved without correction.

## Tests

- **Flip the KNOWN AMBIGUITY test** (`src/parser/docx/numbering-profile-apply.test.ts:280`) into
  a decided-behavior test citing ADR-067: apply-time ilvl-authority is the contract, not an
  ambiguity. Keep the apply-level assertion (divergent tier ignored) since stored legacy rows can
  still reach apply.
- New unit tests on the write schema: divergent styleLadder entry → 422; divergent
  numbering.levels entry → 422; non-empty ladder/numbering without `articleIlvl` → 422;
  omitted `tier` → filled with derived value; fully-consistent profile → accepted unchanged.
- Integration: REST POST/PUT numbering-profile with divergent tier → 422 with the entry-naming
  message; MCP CRUD tool → `isError: true`. Round-trip regression: extract → save → load → apply
  still byte-identical on the four classification fields.
- `openapi.yaml` in the same PR: write-schema description documents the derivation rule,
  `articleIlvl` requirement, and 422; contract gate (`src/api/contract.integration.test.ts`)
  enforces. MCP tool schemas/descriptions updated in lockstep (`src/mcp/contract-map.ts` gates).

## Non-goals

- Threading `tier` through classification (rejected above; ADR-067 records the revisit trigger).
- Any change to `articleIlvl` semantics or the apply/extract round-trip contract.
- Read-schema tightening or data migration of stored profiles.
