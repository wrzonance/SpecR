# Design: DOCX Cross-Reference Extraction via Format-Agnostic Refs Module

**Issue:** [#27](https://github.com/wrzonance/SpecR/issues/27) — `feat(parser): Phase 1c-iii — DOCX cross-reference extraction`

**Date:** 2026-05-18
**Phase:** 1c
**Status:** Approved

## Problem

The `.SEC` parser extracts cross-references into `spec_references` at parse time. The DOCX parser does not. The orchestrator (`src/parser/index.ts:46`) hardcodes `refs: []` for the DOCX path. This blocks DOCX-sourced specs from participating in broken-reference detection (`GET /projects/:id/references/broken`).

## Goal

Add cross-reference extraction to the DOCX parse path with output parity to the SEC parser: refs flow into the `spec_references` table at parse time. Build the extractor as a **format-agnostic module** so future formats (text, PDF, Google Doc DOCX, LibreOffice variants) consume the same logic without reimplementing it.

## Universal Reference Inference

Reference inference must be format-independent. Standards (`ASTM C150`) and section refs (`Section 27 00 00`) appear as plain text in every format — DOCX, plaintext, PDF — and ought to be extracted by one engine operating on the canonical `CsiTree`.

This PR ships the engine and wires it into the DOCX path only. SEC, text, and PDF migration are filed as follow-up issues. SEC keeps its current XML-structured extraction (RID→standard lookups have higher fidelity than regex); the future SEC migration will run both pipelines and dedupe.

## Rules — `src/parser/refs/rules.ts`

```typescript
export interface ExtractionRule {
  readonly id: string;
  readonly description: string;
  readonly pattern: RegExp;
  readonly targetType: 'section' | 'standard';
  readonly examples: readonly string[];
}

export const SECTION_REF_RULES: readonly ExtractionRule[] = [
  {
    id: 'csi-section-keyword',
    description: 'Matches "Section XX XX XX" — standard CSI cross-reference with keyword prefix.',
    pattern: /\bSection\s+(\d{2})\s+(\d{2})\s+(\d{2})\b/gi,
    targetType: 'section',
    examples: ['See Section 09 91 00', 'Section 27 21 00 applies'],
  },
];

export interface StandardOrgPattern {
  readonly orgCode: string;            // 'ASTM', 'NFPA', etc.
  readonly displayName: string;        // 'ASTM International'
  readonly identifierPattern: string;  // regex fragment after orgCode
}

export const STANDARD_ORG_PATTERNS: readonly StandardOrgPattern[] = [
  { orgCode: 'ASTM',   displayName: 'ASTM International',                          identifierPattern: '[A-Z]?\\d+(?:[\\-./]\\d+[A-Za-z]?)?' },
  { orgCode: 'ANSI',   displayName: 'American National Standards Institute',       identifierPattern: '[A-Z]?\\d+(?:\\.\\d+)?(?:[\\-./]\\d+)?' },
  { orgCode: 'IEEE',   displayName: 'Institute of Electrical & Electronics Eng.',  identifierPattern: '\\d+(?:\\.\\d+)?(?:[\\-./]\\d+)?' },
  { orgCode: 'NFPA',   displayName: 'National Fire Protection Association',        identifierPattern: '\\d+[A-Z]?(?:[\\-./]\\d+)?' },
  { orgCode: 'UL',     displayName: 'Underwriters Laboratories',                   identifierPattern: '\\d+[A-Z]?(?:[\\-./]\\d+)?' },
  { orgCode: 'NEMA',   displayName: 'National Electrical Manufacturers Assoc.',    identifierPattern: '[A-Z]+[\\-\\s]?\\d+(?:[\\-./]\\d+)?' },
  { orgCode: 'NEC',    displayName: 'National Electrical Code',                    identifierPattern: '\\d+(?:[\\-.]\\d+)?' },
  { orgCode: 'TIA',    displayName: 'Telecommunications Industry Association',     identifierPattern: '\\d+[\\-./]?[A-Z]?(?:[\\-./]\\d+)?' },
  { orgCode: 'BICSI',  displayName: 'Building Industry Consulting Service Intl.',  identifierPattern: '\\d+(?:[\\-./]\\d+)?' },
  { orgCode: 'ASME',   displayName: 'American Society of Mechanical Engineers',    identifierPattern: '[A-Z]?\\d+(?:\\.\\d+)?(?:[\\-./]\\d+)?' },
  { orgCode: 'ASHRAE', displayName: 'ASHRAE',                                      identifierPattern: '\\d+(?:[\\-./]\\d+)?' },
];

export function buildStandardRefRules(
  orgs: readonly StandardOrgPattern[]
): readonly ExtractionRule[] {
  return orgs.map((o) => ({
    id: `standard-${o.orgCode.toLowerCase()}`,
    description: `Matches "${o.orgCode} <identifier>" — ${o.displayName} standards.`,
    pattern: new RegExp(`\\b(${o.orgCode})\\s+(${o.identifierPattern})\\b`, 'g'),
    targetType: 'standard' as const,
    examples: [`${o.orgCode} 100`],
  }));
}
```

`buildStandardRefRules` is the seam for the future UI: Phase 5 migrates `STANDARD_ORG_PATTERNS` to a `standard_orgs` DB table, populated via CRUD endpoint. The function signature is unchanged — pass DB rows or the constant; downstream extractor doesn't care.

## Extractor — `src/parser/refs/extract.ts`

```typescript
const DEFAULT_RULES: readonly ExtractionRule[] = [
  ...SECTION_REF_RULES,
  ...buildStandardRefRules(STANDARD_ORG_PATTERNS),
];

export function extractRefsFromTree(
  tree: CsiTree,
  rules: readonly ExtractionRule[] = DEFAULT_RULES
): readonly SecRef[] {
  const refs: SecRef[] = [];
  function walk(node: CsiNode): void {
    for (const rule of rules) {
      for (const match of node.text.matchAll(rule.pattern)) {
        refs.push(buildRef(node.id, rule, match));
      }
    }
    node.children.forEach(walk);
  }
  tree.parts.forEach(walk);
  return refs;
}

function buildRef(sourceNodeId: string, rule: ExtractionRule, match: RegExpMatchArray): SecRef {
  if (rule.targetType === 'section') {
    return {
      sourceNodeId,
      targetType: 'section',
      targetSpecSection: `${match[1]} ${match[2]} ${match[3]}`,
      referenceText: match[0],
    };
  }
  // standard
  return {
    sourceNodeId,
    targetType: 'standard',
    standardCode: `${match[1]} ${match[2]}`,
    referenceText: match[0],
  };
}
```

No external dedupe step. If the same regex genuinely matches twice in the same node text, two refs are correct.

## Out of Scope

- SEC parser migration to the shared `refs/` module — follow-up issue.
- Text parser ref extraction — follow-up issue.
- PDF parser (Phase 3, issue #65).
- `standard_orgs` DB table (Phase 5, UI-driven org management).
- CRUD endpoint for adding/removing standard orgs (Phase 5).
- Dedupe between regex-extracted and structurally-extracted refs (only relevant when SEC migrates).
- Validating standard codes against an authoritative registry (e.g. ASTM's actual catalog).
- False-positive suppression beyond what the regex shape enforces (out-of-range XX XX XX patterns naturally don't match; deeper FP analysis = later issue).
- Surfacing refs in MCP tools (refs already flow into `spec_references`; future `get_paragraph` exposure is #56).
