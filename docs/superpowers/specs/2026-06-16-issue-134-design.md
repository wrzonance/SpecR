## 1. Goal

Persist the machine's editability `classification` (from the #133 engine) and the human's
`override` **side by side, never merged** (ADR-022 D2). Effective value =
`override ?? classification.editability`. Re-classification rewrites only the machine field;
the machine never silently undoes a human. This issue is the **DB write-path + read-surface
only** — HTTP endpoints and reclassify orchestration are O-9 (#136), explicitly out of scope.

## 2. Storage (migration `026_paragraph_editability.ts`, reversible)

Two nullable JSONB columns on `paragraphs` — the never-merged contract is physically enforced
because each write touches exactly one column:

```sql
-- up
ALTER TABLE paragraphs
  ADD COLUMN classification       jsonb,   -- machine verdict; NULL until classified
  ADD COLUMN editability_override jsonb;   -- human override;  NULL = none
-- down
ALTER TABLE paragraphs
  DROP COLUMN editability_override,
  DROP COLUMN classification;
```

No `NOT NULL` / no default: `NULL classification` is the honest "not yet classified" state.
(Contrast `source_facts`, migration 023, which defaults `{}` because every paragraph *has*
facts; not every paragraph is classified.)

- **reclassify** → `UPDATE … SET classification = $1` — `editability_override` untouched.
- **set override** → `UPDATE … SET editability_override = $1`.
- **clear override** → `UPDATE … SET editability_override = NULL` → effective falls back to machine.

## 3. Zod boundary (closed schemas) — `src/db/queries/editability.ts`

The payloads are **our own engine output**, fully known — not captured external data. So they
use **closed (`.strict()`) schemas** that reject malformed input, catching engine drift at the
boundary. This is a deliberate, code-commented deviation from the parent design §4's
"all JSONB open/catchall" rule, which exists to preserve *unknown external clues*
(`source_facts`, user convention rules) — a rationale that does not apply here.

```ts
// ClassificationSchema mirrors conventions/ParagraphClassification minus nodeId
// (the row's id IS the nodeId). EditabilitySchema + EvidenceSchema reused from ast/conventions.
const ClassificationSchema = z.object({
  editability: EditabilitySchema,
  confidence:  z.number().min(0).max(1),
  evidence:    z.array(ClassificationEvidenceSchema).min(1),
}).strict();

const OverrideSchema = z.object({
  editability: EditabilitySchema,
}).strict();
```

`EditabilitySchema` already exists (`ast/schemas.ts:67`). `ClassificationEvidenceSchema` does
**not** yet exist — create it mirroring the `ClassificationEvidence` interface in
`conventions/types.ts` (`{ rule: string, fact?: string, detail?: string }`). Place it wherever it
reads best for the closed-schema boundary (e.g. alongside the new `editability.ts` schemas, or in
`ast/schemas.ts` next to `EditabilitySchema` if the AST meta schema also needs it — see §5).

## 4. Write path — `src/db/queries/editability.ts`, re-exported from `src/db/index.ts`

```ts
storeClassifications(specId: string, result: ClassifyResult): Promise<void>
  // one transaction; for each ParagraphClassification:
  //   UPDATE paragraphs SET classification = $1 WHERE id = $nodeId AND spec_id = $specId
  // NEVER writes editability_override → reclassify-safe by construction.

setEditabilityOverride(paragraphId: string, editability: Editability): Promise<void>
  // UPDATE paragraphs SET editability_override = $1 WHERE id = $paragraphId

clearEditabilityOverride(paragraphId: string): Promise<void>
  // UPDATE paragraphs SET editability_override = NULL WHERE id = $paragraphId
```

- `ClassifyResult` / `ParagraphClassification` are imported from `../../conventions/index.js`
  (module-barrel boundary). `nodeId` on each result IS the `paragraphs.id`.
- Wrap DB failures in `DatabaseError` with `cause` chained (CLAUDE.md module-boundary rule).
- Bulk store is the only store granularity — the engine emits a whole-spec `ClassifyResult`
  and O-9 reclassify rewrites a whole spec; a per-node store has no caller (YAGNI).

## 5. Read surface — `getSpecTree` only (no new read function)

In `src/db/queries/specs.ts`:

1. `ParagraphTreeRow` gains `classification: unknown` and `editability_override: unknown`
   (validated, not trusted, in `buildNodeTree`).
2. The `getSpecTree` SELECT adds `classification, editability_override`.
3. `buildNodeTree` parses both via the closed schemas and conditionally spreads an optional
   `editability` sub-object into `meta` — **omitted entirely when `classification` is NULL**,
   mirroring the existing `conflicts` / `sourceFacts` "omit-when-empty" pattern:

```ts
meta.editability?: {
  value:      Editability                        // effective = override ?? classification.editability
  confidence: number                             // machine confidence
  evidence:   readonly ClassificationEvidence[]  // machine why-chain
  override?:  Editability                         // present ONLY when a human override exists
}
```

When an override exists, `value === override` and the machine's verdict remains readable
(its `evidence` explains what was overridden — enabling the O-15 machine-vs-human badge).

4. `SpecNodeMeta` (`ast/types.ts`) gains the optional `editability` field; `SpecNodeMetaSchema`
   (`ast/schemas.ts`) gains the matching optional object. MCP/REST tree readers inherit it for free.

## 6. Error handling

- `editability.ts` wraps all PG errors in `DatabaseError` (`src/db/errors.ts`) with `cause`.
- Zod parse failures at the read boundary chain the `ZodError` as `cause` — a corrupt row is a
  loud `DatabaseError`, never a silent drop.

## 7. Tests (integration against real PostgreSQL; unit for schemas)

Integration (`src/db/queries/editability.integration.test.ts` + extend specs tree test):
- `round-trip: store classification → getSpecTree reads back identical`
- **`override survives reclassify`** — set override, re-run `storeClassifications` with a
  *different* machine verdict; assert `meta.editability.value` still equals the override and
  `evidence` reflects the new machine pass (decisive named test, parent §7).
- `clearEditabilityOverride restores machine classification as effective`
- `getSpecTree surfaces effective editability + evidence on every classified paragraph`
- `storeClassifications is scoped — does not write a sibling spec's paragraphs`

Unit (`editability.test.ts`):
- closed schema rejects confidence > 1 / < 0 and empty evidence (`// `-documented).
